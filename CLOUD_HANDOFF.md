## Цель пользователя

Исправить причины слишком медленного движения плит и сделать модель
физически согласованнее. Пользователь разрешил реализацию, проверки и
следующие шаги без повторного согласования обычных технических действий.
Он ожидает конкретный результат и отчёт после каждого этапа.

Скорость не подгонять к земным 5 см/год. Более обоснованная модель может дать
как большую, так и меньшую скорость. Не назначать случайное направление
погружения, номер плиты или искусственный коэффициент ради ускорения.

## Где остановились

Есть три разных пути; их нельзя считать уже объединённой моделью:

1. **Рабочая механика `young-mechanics-0.5` и GUI.** Ранее исправлены источник
   мантийной нагрузки, локальные свойства, геометрия тепловых порций слэба,
   погружение и сопротивления. Эта ветка продолжает использовать прежний
   растровый перенос. Отрыв по скалярной прочности и ряд физических
   приближений остаются ограничениями.
2. **Связанный дробный эксперимент.** Перенос долей материала, локальное
   охлаждение и базальная динамика работают отдельно. Время рождения и
   удаления материала учитывается схемой `gauss2_v2`. Полная контактная
   механика, тяга слэбов и разрушение к нему ещё не подключены.
3. **Новая сохраняемая геометрия и строгий допуск поддвига.** Полигональные
   фрагменты на сфере, действительные контактные дуги внутри смешанных
   ячеек, локальная направленная память и пассивный слэбовый архив. Силы
   и тепловая обратная связь здесь ещё не включены; движение задано.

Последнее реализованное изменение — **механический допуск вынужденного
поддвига по явно заданному наклонному слабому разлому**. Он проверяет:

- сближение по всей дуге, включая внутренние экстремумы скорости;
- сжатие на плоскости и знаковую касательную нагрузку в сторону погружения;
- кулоновское сопротивление с явно заданными сцеплением и трением;
- реальную локальную геометрическую опору и согласованность истории.

Тензор эффективного напряжения задаётся в глобальных декартовых координатах
в середине дуги, со сжатием положительного знака. Пространственная модель —
однородное локальное нагружение с параллельным переносом вдоль дуги.
Все численные физические параметры явные. Снимок нагрузки привязан к точной
поверхности и времени и не переносится автоматически на следующий шаг.

Это **не решение самопроизвольного или самоподдерживающегося зарождения
субдукции**. Нет расчёта возникновения наклонной плоскости, контактного
напряжения, изгиба или деформационного сжатия при отказе. Недопустимый
геометрический шаг отклоняется атомарно, до изменения материала.

## Ближайшая задача

Продолжить механическую часть первого оставшегося этапа: связать новый
допуск с физически согласованным **контактным нагружением и ориентированной
геометрией разломов**, а затем с сопротивлением изгибу. Не считать этот
пункт завершённым только потому, что создан проверяющий интерфейс.

До изменения кода сопоставить существующие механизмы, чтобы не создавать
вторую копию того же закона:

- `genesis_starter.py`: эффективный касательный stress proxy, а не решённое
  полное контактное напряжение;
- `genesis_plate_membrane_diagnostic.py`: статическая диагностика со
  свободными краями; не живой решатель контакта и повреждения;
- `genesis_faults.py`, `genesis_fault_law.py`: касательная слабая линия,
  signed shear и пластический закон, но не радиальный наклон разлома;
- `young_slab_sinking.py`, `young_slab_constraints.py`, `young_plate_dynamics.py`:
  существующая механика погружения и сил для прежнего представления.

Выбрать и явно описать сокращённую физическую постановку, её нагрузки,
степени свободы, диссипацию и границы применимости. Если модель использует
заданные слабые плоскости как начальные условия, так и называть их;
это не автоматически возникшие разломы. Симметрия и конфликт истории
не разрешаются сортировкой ID, максимальной массой или выбором последней записи.

Критерии следующего результата: однозначный физический источник всех входов,
инвариантность к системе координат и нумерации плит, сохранение материала,
согласованные единицы и направления сил, отсутствие двойного учёта тяги,
обоснованное поведение при заблокированном сближении, воспроизводимый restart.
Не обещать рост скоростей до включения и проверки полного баланса сил.

## Остальные крупные блоки

После решения ближайшей задачи остаются:

1. Объединить время геометрических событий с уже реализованным охлаждением.
2. Распределить слэбовый материал вдоль дуг; рассчитывать отдельное движение
   погружённого тела, растяжение и утонение шейки с сохранением объёма,
   физический отрыв. Подключить тягу, хребты и контактные реакции.
3. Связать живые напряжения и переносимую тензорную память с разрушением,
   новыми разломами и сменой топологии.
4. Включить новую механику в штатный цикл, версии сохранений и GUI.
5. Проверить длительную эволюцию и сходимость по времени/сетке, затем
   производительность без удаления материальных историй ради ускорения.

Совместное сохранение геометрии и слэбов уже готово. Его не надо писать
заново. Континенты, осадки, повторное плавление и выход за область молодой
опорной колонки пока не поддержаны в новом экспериментальном пути.

## Облачная среда и команды

Численный путь работает на CPU. CUDA и GUI для текущего этапа не нужны.
Предпочтителен Python 3.12. Создать новую среду в облаке; не переносить `.venv`.

```bash
git clone --branch fix/genesis-mantle-convection https://github.com/TopoLM21/Habitable-Moon-Project.git
cd Habitable-Moon-Project
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-cloud.txt
python scripts/cloud_handoff.py restore
python scripts/cloud_handoff.py verify
python scripts/run_cloud_tests.py
```

Если репозиторий уже подготовлен облачной средой, первые две команды не
нужны: проверить ветку и SHA, затем использовать её каталог. `requirements.txt`
добавляет инструменты графики и GUI, если они понадобятся позже.

Локальная проверенная среда: Python 3.12.14, NumPy 2.5.2, SciPy 1.18.1,
PyYAML 6.0.3, pytest 9.1.1. Файл `requirements-cloud.txt` задаёт минимальные
требования; установленные версии записывать в новых результатах. Облачный
Linux-runtime этой передачей ещё не проверен: локальная проверка экспортированной
копии не заменяет запуск тестов в облаке.

Положительный синтетический опыт:

```bash
python analysis/geometric_initiation_validation/admission_case.py --out results/cloud_admission_control
```

Проба реального источника (длится несколько минут; ожидаемый код возврата **2**):

```bash
python run_geometric_initiation_probe.py --source analysis/slab_sinking_followup/runs/ordered_sub4_dt1/elapsed_0050 --out results/cloud_saved50_admission --dt-myr 0.25 --inherit-legacy-polarity
```

Код 2 здесь означает явный `unresolved_initiation`, а не падение Python.
Без новых механических входов именно этот результат ожидается. Нельзя
«исправлять» его отключением проверки. Все выходные каталоги должны быть новыми.
