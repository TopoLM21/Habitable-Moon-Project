# CPU: численные ускорения и цикл ячеек

2026-09-03. Экспериментальный worktree `perf/cpu-parallel`, поверх `0bfb810`
и однократной подготовки сетки. Физическая модель и чекпойнты остаются v0.31.
Стабильный worktree и исходные пользовательские результаты не изменены.

## Что теперь включено

При выборе оптимизированного CPU-режима в GUI автоматически используются:

1. Пакетное усреднение трёх соседей для контраста корней литосферы. Кэшируются
   только индексы соседей, а не значения поля: они берутся из текущего состояния.
   Для иной связности сохранён исходный цикл.
2. Расчёт отрицательной плавучести одной-двух ячеек при выборе стороны
   субдукции, без повторного построения полного массива для каждого запроса.
3. Пакетный перенос полей ячеек с **ровно одним источником** консервативного
   переноса. В проверенном отрезке это около 90% ячеек. Сортировки и маленькие
   операции NumPy на каждой такой ячейке больше не нужны.

Перекрытия плит, выбор победителя при столкновении, общие суммы потерь,
перераспределение континентального материала и обработка разрывов остаются
в исходном коде и прежнем порядке. Последовательность шагов, шаг времени,
точность float64 и разрешение не менялись. Новые пакеты не устанавливались.

Потоковый вариант третьего участка также реализован: 1/2/4/8 работников,
отдельный постоянный пул, только чтение старого состояния. Работники возвращают
частные массивы; координатор записывает их после успешного завершения всех
заданий. Ошибка подготовки не оставляет частично записанный результат.

**По умолчанию оставлен один работник ячеек.** Дополнительные потоки не дали
убедительной экономии полного времени на основной сетке. Это не отключение
ускорения: быстрый пакетный путь работает и с одним работником.
Существующие настройки GUI по-прежнему означают работников **переноса плит**
и процессы **отрисовки карт**, а не этот новый пул.

Исходный CPU-режим сохраняет старые численные пути. В оптимизированном CLI
для контрольных сравнений доступны `--no-numeric-kernels`,
`--no-single-source-cells` и экспериментальный `--cell-workers 1|2|4|8`.
Флаг `--cell-kernels` по-прежнему относится только к ранее ускоренным осадкам.
Фактические новые настройки, число обработанных ячеек и ID исполнявших их
потоков сохраняются в `render_timings.json` → `numerical_execution`.

## Полное время, не скорость отдельной функции

700→720 Myr, dt=4, 20 480 ячеек, однократная подготовка, один работник
переноса плит, четыре процесса карт, пакетные осадки, below-normal priority.
Каждый замер — новый процесс; случаи выполнялись последовательно, во втором
повторе порядок полностью обращён. Здесь нет cProfile и таймеров функций.

| Численный режим | Повтор 1, с | Повтор 2, с | Медиана, с |
| --- | ---: | ---: | ---: |
| Прежние численные пути | 32.653 | 32.251 | 32.452 |
| Два небольших ускорения | 30.731 | 31.095 | 30.913 |
| Также пакетный цикл ячеек, 1 работник | 24.211 | 23.832 | **24.021** |
| То же, 2 работника ячеек | 23.967 | 23.466 | 23.716 |
| То же, 4 работника ячеек | 23.975 | 24.135 | 24.055 |
| То же, 8 работников ячеек | 24.026 | 23.377 | 23.701 |

Текущий вариант по умолчанию сократил медиану полного сегмента примерно
на **26%, или 8.4 секунды** (ускорение 1.35×). Два небольших ускорения сами
по себе дали около 4.7%; основная прибавка — пакетный цикл ячеек.
Разница вариантов с 1 и 8 работниками — лишь около 1.3%, меньше убедительного
запаса на разброс этих коротких замеров. Все образцы приведены, исключений нет.

На компьютере присутствовали процессы ComfyUI; их не останавливали, загрузка
не фиксировалась. Поэтому это локальные замеры, не статистически строгая оценка
и не обещание ETA полного прогона 4.5 млрд лет. Большая финальная сборка GIF
время этого промежуточного сегмента не включает. Прежние более быстрые замеры
другого дня/серии не используются как база сравнения.

## Где теперь тратится время

Отдельная пара с лёгкими таймерами, 700→720 Myr. Это непересекающиеся
интервалы координатора, не суммы вложенных вызовов или времён процессов карт:

| Участок | Прежний путь, с | Новый путь, с |
| --- | ---: | ---: |
| Выбор владельцев и перенос полей ячеек | 6.708 | **0.397** |
| Из них новый пакетный путь | — | 0.029 |
| Контраст корней | 1.549 | 0.025 |
| Память субдукции | 1.824 | 0.802 |
| Динамика плит без вложенной классификации границ | 2.436 | 1.819 |
| Расчёт вулканических дуг | 3.975 | **4.021** |
| Транспортная карта | 3.377 | **3.198** |

В новом времени цикла 0.397 с учтены и пакетная обработка, и оставшийся
последовательный цикл перекрытий. Потоки ускоряют только первый, уже маленький
кусок. На участках со слияниями/разделениями он занимал 0.027 с с одним работником
и 0.042 с с восемью. Поэтому разницу общего времени в процентах нельзя приписывать
полезному масштабированию этого пула.

Диагностические полные времена всех случаев также сохранены в сводке:
слияния 22.141/21.331 с, разделения 22.969/38.858 с для 1/8 работников;
700→720 38.788/22.329 с для старого/нового пути. Медленный случай разделений
содержал 20.392 с в выводе отчётных карт, при 11.429 с в физике: этот выброс
не скрыт и не доказывает замедление физики от потоков. Для основной оценки 26%
используется только отдельная повторная серия без этих таймеров.

Следующий разумный кандидат — `compute_volcanic_arc_forcing`: сначала уменьшить
повторный перебор границ для каждой зоны субдукции и повторную геометрическую
работу; затем измерить, стоит ли распараллеливать подготовку вкладов. Общую запись
в поле и порядок объединения вкладов надо сохранить. Этот следующий участок
**в текущем этапе не менялся**. Нынешняя пакетная организация пригодна как
подготовка к GPU-исследованию, но сама по себе не является GPU-бэкендом.

## Проверки

В основной серии из 12 запусков побитово совпали все 62 массива чекпойнта,
полные метаданные/история и все 40 PNG каждого случая. Сравнение выполнено
с ранее сохранённым независимым эталоном, не только между новыми режимами.

Участки 320→340 Myr со слияниями и 620→640 Myr с разделениями проверены
отдельно при 1 и 8 работниках ячеек. Все 62 массива, полные метаданные и
40 PNG каждого случая совпали с ранее сохранёнными эталонами.

Свежий старт 0→4 Myr на **81 920 ячейках** также совпал с прежним эталоном:
все 62 массива, метаданные и 47 PNG во всех трёх режимах. Одно последовательное
сравнение без таймеров: прежний путь 63.821 с, новый с 1 работником 57.958 с,
с 8 работниками 57.825 с. Это проверка более плотной сетки и короткого свежего
старта, не оценка скорости длительной интеграции на этом разрешении.
Первый тест с неверно заданным интервалом кадров 20 вместо 4 Myr сохранил
точное состояние, но не вывел восемь ожидаемых кадров; он сохранён отдельно,
не участвует в сравнении времени и повторён с одинаковым интервалом 4 Myr.

Модульные проверки покрывают режимы 1/2/4/8 работников, наличие и отсутствие
необязательных полей состояния, старый неконсервативный перенос, знаки нуля,
неизменность входных массивов, отсутствие частичной записи при ошибке,
независимость пулов и их очистку, включая ошибку создания второго пула.
Полный набор `python -m pytest -q`: **274 теста прошли**, 42.93 с.

Новый оптимизированный runner создал чекпойнт 708 Myr; его продолжили до
720 Myr и новым runner, и **неизменённым runner стабильного worktree**.
Оба результата точно совпали со стабильным эталоном: 62 массива и вся
история/метаданные. Новый формат чекпойнта или конвертация не требуются.

Реальный контроллер GUI (Qt QProcess, без открытия окна): свежие сегменты
0→4→8→12 Myr, безопасная пауза на 4 Myr, возобновление и финальная сборка.
Все три чекпойнта, **127 PNG и 10 GIF побитово совпали** с прежним эталоном.
Логи каждого сегмента подтверждают включение новых численных путей по умолчанию.
После завершения тестов процессов «Спутника» не осталось; посторонние процессы
ComfyUI не затрагивались.

Полные результаты текущего этапа находятся в `results/cpu_performance/numeric_*_20260903`.
Сырые чекпойнты и изображения исключены из Git. Компактная сводка:
`performance_reports/numeric_kernels_study.json`; повторная сборка сводки и
проверка GUI-результатов: `python analysis/summarize_numeric_study.py`.
Исходники, тесты и отчёты этого этапа относятся к экспериментальной ветке
`perf/cpu-parallel`; в стабильную `main` они не влиты.

## Воспроизведение

Из корня экспериментального worktree, в его `.venv`, с новой выходной папкой:

```text
python analysis/profile_cpu_stages.py --config results/gui_runs/stable_copy_0_700/gui_runtime_config.yaml --resume results/gui_runs/stable_copy_0_700/gui_checkpoint_000700_Myr --end-time 720 --output results/cpu_performance/NEW_numeric_comparison --modes after --numeric-modes legacy kernels cells1 cells2 cells4 cells8 --repeat 2 --plain --reference results/cpu_performance/baseline_full/checkpoint_720 --reference-pngs results/cpu_performance/baseline_full
```

`legacy` отключает только новые численные пути, сохраняя другие уже проверенные
CPU-ускорения. `kernels` включает первые два изменения, `cellsN` — все три
с N работниками ячеек. Без `--plain` добавляются диагностические таймеры этапов;
их время нельзя смешивать с обычными замерами. `--cprofile` предназначен только
для поиска дорогих вызовов. Для свежей сетки: `--subdivisions 6` без `--resume`.
Не запускать измерения одновременно с другим прогоном «Спутника».
